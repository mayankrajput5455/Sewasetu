What We Learned

Design Insights from Eval Runs

Key findings from testing the MCP servers against real citizen scenarios

🛡️

Validation Parity is Critical

MCP tools must enforce identical validation to the web portal. Early eval runs caught a case where the bank account regex wasn't applied — fixed by using the shared portal_db.validate_application() function in both channels.

📱

OTP Flow for Elderly Users

Elderly citizens on shared phones may not immediately have the OTP. The assistant must ask, wait, and confirm rather than timing out. We added explicit guidance in the tool description for AI clients to handle OTP retrieval gracefully.

🔀

Separation of MCP Endpoints

Running citizen and officer servers on separate ports (8001 vs 8002) enforces the access boundary at the network level. No citizen token can accidentally reach officer tools even if the AI agent tries.

📋

Audit Trail Completeness

Every MCP action writes to audit_log with the actor prefixed citizen: or officer:, making MCP-originated actions distinguishable from web portal actions in the admin view.

⚠️

Age Proof via MCP

AI-submitted applications flag doc_path as mcp_verbal_declaration. Officers are shown a clear warning in the officer assistant view, prompting them to request the physical document before approving.

🌐

Block Validation Early

The check_eligibility tool eliminates wasted OTP flow for citizens in ineligible blocks. Eval showed this prevents frustration for citizens in Guwahati who heard about the scheme but aren't in covered blocks.
